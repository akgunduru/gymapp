# System Architecture

## Target Architecture

Social Gym System will be a modular full-stack monolith built with Next.js 15, TypeScript, App Router, Tailwind CSS, shadcn/ui, PostgreSQL, Prisma ORM, and credentials-based authentication.

The system should keep each feature isolated while still using a single deployable application and one PostgreSQL database.

## High-Level Components

| Layer | Responsibility |
| --- | --- |
| App Router | Route groups, layouts, server components, protected pages |
| UI components | Shared shadcn/ui wrappers and app-specific reusable components |
| Feature modules | Auth, profile, gyms, matching, workouts, nutrition, professionals, consultations, messages, admin |
| Server actions/API routes | Mutations, uploads, auth-sensitive operations |
| Services | Business logic such as matching, mock AI analysis, authorization checks |
| Prisma | Type-safe database access |
| PostgreSQL | Persistent relational storage |
| Local uploads | Meal images and professional certificates |

## Module Boundaries

Each feature should own:

- Zod schemas for forms and actions.
- Server actions or route handlers for mutations.
- Data access functions for that feature.
- UI components that are specific to the feature.
- Types that are not already generated by Prisma.

Shared code belongs in `src/lib` or `src/components/shared` only when it is used by multiple modules.

## Authentication Strategy

Recommended MVP choice: NextAuth credentials provider or a simple JWT/session-cookie implementation.

Credentials flow:

1. User submits email and password.
2. Server validates input with Zod.
3. Password is checked with a hash.
4. Session stores user id, email, and role.
5. Protected routes check session.
6. Server actions re-check authorization before mutating data.

The UI must not be the only enforcement point. Every sensitive server action must call authorization helpers.

## Role-Based Access Control

Create helpers with clear intent:

- `requireUser()` for authenticated users.
- `requireRole(role)` for exact role checks.
- `requireAnyRole(roles)` for role groups.
- `assertOwnerOrAdmin(ownerId)` for records owned by a user.

Examples:

- Admin verification actions require ADMIN.
- Updating a profile requires owner or ADMIN.
- Professional profile updates require matching role or ADMIN.
- Viewing messages requires membership in the conversation.

## Data Flow

```txt
Browser UI
  -> Server Component fetches data through feature data functions
  -> Prisma reads PostgreSQL
  -> UI renders typed view models

Browser form
  -> Server Action or API route
  -> Zod validation
  -> RBAC helper
  -> Feature service
  -> Prisma mutation
  -> Revalidate route / redirect / return action state
```

## File Upload Architecture

Use local disk storage for MVP:

```txt
public/uploads/
  meals/
  certificates/
```

Upload rules:

- Accept common image formats for meals: jpg, jpeg, png, webp.
- Accept pdf/jpg/png for certificates.
- Enforce file size limits.
- Generate safe filenames.
- Store only the relative public path in the database.
- Never trust original filenames for storage paths.

## Map and Location

- Use Leaflet with OpenStreetMap tiles.
- Store gym latitude/longitude.
- Store user approximate latitude/longitude.
- MVP matching can calculate distance with the Haversine formula in application code.
- No paid geocoding service is required.

## Mock AI Meal Analyzer

The mock analyzer must be isolated so it can later be replaced.

Input:

- Uploaded image path or metadata.
- Optional user text description.

Output:

- Estimated meal name.
- Calories.
- Protein, carbs, fat.
- Confidence score.
- Explanation string showing that this is a demo estimate.

The module should not call external services.

## Seed Data Strategy

Seed data should include:

- One ADMIN user.
- At least two USER accounts.
- At least one TRAINER and one DIETITIAN account.
- Gyms with coordinates.
- Exercises by muscle group and level.
- Workout templates.
- Example verified and pending professional profiles.
- Example conversations/messages.

## Environment Variables

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | PostgreSQL connection string |
| `AUTH_SECRET` or `NEXTAUTH_SECRET` | Session/JWT signing |
| `NEXTAUTH_URL` | Required when using NextAuth |
| `UPLOAD_DIR` | Optional local upload directory override |

## Non-Goals

- No microservices.
- No external AI service.
- No cloud object storage for MVP.
- No real-time messaging server.
- No complex background job queue.
